# Sgraffito Sampler - Implementation Findings

**Date:** 2026-11-10  
**Scope:** Review of code, tests, presets, and documentation against plan `docs/plans/04_sgraffito-sampler-plugin.md`

## Executive Summary

The Sgraffito sampler plugin has a solid foundation. Core engine (Phase 1) exists in `core_dsp` with tests passing, the processor and editor are complete, and factory presets are present. However, several critical phases appear incomplete or partially implemented, and some design choices could be improved.

## What's Working Well

### 1. Core DSP Engine (Phase 1)

- **SamplerEngine.h** implements memory traces, tape-stop ramps, voice pool, Lorenz chaos drift, and scale lock
- **SamplerMaps.h** handles key-to-region mapping, chop slices, and shuffle permutations
- Seven dedicated DSP tests verify: region mapping, chop map, shuffle, tape stop, memory trace, ghost threshold, and scale lock
- All CoreDSPTests pass consistently

### 2. Plugin Architecture (Phase 2)

- 71 parameters with proper APVTS integration
- Voice pool of 32 voices with stealing logic
- MIDI note-on/off correctly allocates/releases voices
- State round trip works for all parameters
- Atomic buffer swap for thread-safe sample access

### 3. Sample Loading (Phase 3)

- FLAC embedding up to 20 MB limit
- WAV, AIFF, and FLAC file support with resampling
- Atomic buffer swap for thread safety
- Path fallback and missing-file handling

## What's Missing or Incomplete

### Phase 4: Modes

- **Scrub mode** - region mapping logic present but not verified in tests
- **Chop mode** - slice count control exists but slice coverage test incomplete
- **Cloud mode** - grain scheduler referenced but not fully implemented
- **Swell mode** - reverse playback and crossfade logic absent

### Phase 5: Creative Features

- **Lay Back** - timing offset per note not implemented
- **Scale Lock** - quantization to scale works in processor but no test coverage
- **Memory** - trace movement and decay present but not tested
- **Drift** - Lorenz attractor integration exists but drift multipliers unverified

### Phase 6: Editor

- **Waveform display** - placeholder only, no actual waveform rendering
- **Key map strip** - absent from layout
- **Mode selector** - functional but not visually integrated

### Phase 7: Modulation

- Router integrated but target table limited to 24 entries (missing some controls)
- No test for routed modulation on audio

## Key Issues and Solutions

### Issue 1: Incomplete Mode Implementation
**Problem**: The processor.cpp references mode constants but doesn't switch behavior per mode. All modes fall back to the same playback logic.

**Solution**: Add a `switch(mode)` in processBlock that routes to different region calculation, grain scheduling, or playback direction based on the selected mode.

### Issue 2: Missing Waveform Display
**Problem**: The editor shows no waveform - just a blank area where it should render the sample with region markers and slice lines.

**Solution**: Implement `paint()` in PluginEditor.cpp to draw the sample waveform using `Graphics::drawLine` for each frame, overlay region markers as vertical lines, and add slice lines for chop mode.

### Issue 3: Grain Scheduler Not Implemented
**Problem**: Cloud mode references grainSize, grainDensity, grainSpread parameters but doesn't actually generate grains.

**Solution**: Create a simple grain scheduler in processBlock that reads from the voice's region at random positions, jittered across stereo and pitch, with decay after release.

### Issue 4: Lay Back Timing
**Problem**: The layBack parameter exists but notes are not delayed relative to the grid.

**Solution**: In processBlock, when a note-on arrives, calculate `scheduledPosition = midi.samplePosition + delaySamples` where delaySamples comes from `layBackParam->load()`. This requires storing pending note-ons in a queue and writing them at the correct sample offset.

### Issue 5: State Persistence for Sample
**Problem**: The embedded FLAC bytes are not saved with the state, so they must be re-encoded on reload (inefficient).

**Solution**: Store the flacData as a child element of the `<PARAMETERS>` node in SuiteState::write() and read it back in SuiteState::read().

## Recommendations

1. **Add missing tests** - Write plugin-level tests for each mode's defining behavior before claiming completion
2. **Render the waveform** - Implement visual feedback for the loaded sample; this is critical for user trust
3. **Implement grain scheduler** - Even a simple random-grain reader will make Cloud mode functional
4. **Add delay queue for lay back** - This requires careful timing but is essential for the genre feel
5. **Consider a "reset memory" action** - The plan mentions this but it's not in the processor
